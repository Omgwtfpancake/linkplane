# Linkplane — Local API Design

> Design pass, 2026-09-11. **Design only: no endpoint is implemented.** Constrained by
> `docs/api-invariants.md`; vocabulary from `docs/current-state.md`; states from
> `docs/state-machines.md`; wire shapes from the code as it stands at commit `9ae0cd7`
> (package `0.3.0`, contract version 2, 436 hermetic tests). Where this document and the
> code disagree, the code is right and this document has drifted.

**Guiding principle:** *Expose Linkplane. Do not rebuild Linkplane.* — One capability
model, many interfaces. **The API exposes Linkplane's domain; it does not expose
Linkplane's implementation.**

> **Implementation status:** Slice 0 landed in `036f577`; Slice 1 (the listener) in
> `6dcf570`/`674378f`; Slice 2 (cancel, rules, reload, audit, public projections) is
> implemented — see ADR 0012, `docs/openapi.json` (generated by
> `python -m linkplane.api.openapi`), and `docs/api-contracts.md`. Details that differ
> from the text below: the OpenAPI document is JSON (stdlib has no YAML parser for the
> pin test); `backup.photos` `source` must be an absolute Android path (the service's
> default is `/sdcard/DCIM/Camera`), not `DCIM`; **the public Job `action` is the
> capability name** (`backup.photos`) with the record's own name in `job_action`
> (§10.1); every device-associated projection carries `device_id` (§6.2);
> `camera.capture` stays out of the action runtime by founder decision (§25).
>
> **Founder review, 2026-09-11 — approved for implementation with amendments.** D1–D5 are
> decided (§26). Six amendments are folded in below and marked *(review)*: no `provider`
> in the ordinary action request (§8); execution mode is declarative, not inferred from a
> function signature (§9); canonical device identity is `device_id`, names are aliases
> (§6); SSE authentication uses the `Authorization` header via streaming `fetch`, never a
> URL token (§12.3); client provisioning is a Slice 0 deliverable (§16); explicit
> sensitive-data logging rules (§18). Paths carry `/v1` (D3); `/v1/events/stream` carries
> canonical Events only (D4); `read` excludes both `audit.read` and `rules.read` (D5).

```text
                         ┌── CLI                      (today: direct service calls + control socket)
                         ├── Local HTTP API           (this design)
Linkplane Core / Daemon ─┼── future Desktop GUI       (an HTTP API client)
                         ├── future SDK               (an HTTP API client)
                         └── future MCP               (an HTTP API client)
```

## 1. Goals

1. Expose the existing control plane — Device, Capability, State, Event, Action, Job,
   Rule, Audit, Provider, Result, Error — over local HTTP, using the same typed services,
   daemon, observed state, canonical event stream, job runner, audit writer, and `LP-`
   error codes the CLI uses.
2. Give a GUI, an SDK, an MCP server, or an agent one way to ask "what devices exist, what
   is true about them, what can I do, do it, what happened".
3. Keep streaming first-class: the canonical event stream is resumable from `seq`.
4. Answer "who requested this?" for every action, with a scope model small enough to
   implement in one slice and honest enough that no future client automatically gets
   unrestricted device control.
5. Stay stdlib-only, local-first, and boringly reliable.

## 2. Non-goals

Not in this design or its implementation milestone: remote/Internet access, cloud
accounts, OAuth, full RBAC, multi-user servers, MCP, GUI, SDK generation, plugin or
workflow marketplaces, a native Android agent, device farms, AI execution, per-action
human approval gates (vision §22), consent receipts (§23), privacy classification (§24),
a shell-execution endpoint (never), and rule editing over HTTP (see §25).

## 3. Existing architectural constraints

Facts read from the repository that shape every decision below.

| Fact | Where | Consequence for the API |
|---|---|---|
| `linkplaned` hosts the only `Observer`, the `HistoryWriter` (owner of `seq`), the `JobRunner` (owner of the "one running job per device+action" set), the `AuditWriter`, and the rules `Engine` | `daemon.py` | The API must live **inside the daemon process**. A separate API process would need its own `JobRunner` (a second job model), its own audit writer, and a widened socket protocol for every action. ADR 0008 already names the daemon as "the natural host for … an API". |
| Control socket protocol `linkplane.daemon/1`: `status`, `state`, `subscribe {types, devices}`, `reload`, `stop`; newline-delimited JSON; one request per connection; `subscribe` is one-way after the acknowledgement | `daemon.py::_Handler` | Streaming is server → client only; nothing in the repository sends a client message after subscribing. |
| `Event` wire shape is `Event.to_dict()` with `"schema": "linkplane.event/1"`; `seq` is a per-history-file monotonic integer that continues across restarts; `event_id` is an opaque uuid | `core/events.py`, `history.py` | `seq` is the only ordered identifier; `event_id` cannot be used for continuation. |
| Subscriber fan-out is a bounded queue (1000); a slow subscriber **drops** events with a warning | `daemon.py::Subscriber.offer` | A live stream can have gaps; `seq` makes them detectable; history makes them recoverable. |
| Events are "domain changes only", written only by the observer via `core.state.diff` | ADR 0007, `docs/current-state.md` output channels | An action does not produce an `Event`; job and audit records are their own record types. |
| Job states `running · retrying · completed · failed · cancelled · skipped`; creation is immediate (no queue); duplicates are recorded as `skipped`; `JobRunner.run()` is synchronous and returns the final record; cancellation is by device or all, not by id | `jobs.py`, `docs/state-machines.md` | A 202 needs a way to get the record id before completion; cancel-by-id is additive work. |
| `JobRecord.action` uses the rules-file vocabulary (`backup`, `send`, `clipboard-sync`); duplicate detection keys on `(device, action)` | `jobs.py`, `actions.py` | An API-started backup must use the same job action name as a rule-started one, or two backups could run concurrently on one device. |
| Audit `linkplane.audit/2`: `schema, audit_id, ts, kind, actor, source, decision, device?, rule?, job_id?, action?, correlation_id?, details`; `decision` is closed; `kind` is open; `actor` is a string (`daemon`, `rule:<name>`) | `automations.py::AuditWriter` | `actor: client:<id>` and new `action.*` kinds fit without a schema bump. |
| `CapabilityReport(name, status, detail, requirements, metadata)` with five statuses, reported **per provider**, in catalogue order; the catalogue is append-only | `core/capability.py`, ADR 0004 | Capability names are the action identifiers and the scope vocabulary. |
| `LinkplaneError.to_dict() → {type, message, code, hints}`; codes are never renumbered, may be added; every code needs a title (`tests/test_core_errors.py`) | `core/errors.py`, ADR 0005 | The HTTP error body is this object; new API conditions get new codes, not a new shape. |
| `OperationResult(value, error, operation, resource_id, provider, warnings)`; no `to_dict()` today; services render `value` | `operations.py` | The action Result representation is a projection of these fields (additive `to_dict()`). |
| Device selection (profile → serial / SSH endpoint, conflicts, `auto` fallback) lives in `cli.py::apply_device_profile` and `providers.select_provider` | `cli.py:671–770` | The registry/target resolver must be **extracted** into a shared module before the API can reuse it; the API must not copy it. |
| Registry identity: profile name, or `serial:<x>` for an unpaired observed device (`Observer.device_name`) | `observe.py`, `cli.py::profile_identities` | `{device_id}` in URLs is that name, never an address. |
| Only the Unix socket's `0600` mode authenticates today | ADR 0008 | Loopback TCP is reachable by every local user; a token is mandatory there. |
| Stdlib only (ADR 0001) | `pyproject.toml` (`dependencies = []`) | `http.server.ThreadingHTTPServer` + a small router; no framework. |

## 4. Resource model

The smallest hierarchy that maps one-to-one onto existing records:

```text
/v1/health                                  daemon describe() + API/protocol/client info
/v1/devices                                 registry: profiles ∪ observed devices
/v1/devices/{device_id}                     identity, providers, connection summary, embedded state
/v1/devices/{device_id}/state               DeviceState (observed)                 ← "what is true"
/v1/devices/{device_id}/capabilities        CapabilityReport[] per provider         ← "what can I do"
/v1/devices/{device_id}/actions             POST: typed action → Result (200) | Job (202)
/v1/jobs, /v1/jobs/{job_id}                    JobRecord                              ← "what happened (long)"
/v1/jobs/{job_id}/cancel                    POST (slice 2)
/v1/events                                  Event history by seq
/v1/events/stream                           Server-Sent Events (live, resumable)
/v1/audit                                   audit entries (slice 2)
/v1/rules, /v1/rules/reload                    LoadedRules; the file stays the source (slice 2)
```

Evaluated and rejected:

- `POST /backup`, `POST /notify`, `POST /adb-command` — command-shaped routes would be a
  second vocabulary next to the capability catalogue and would invite a shell endpoint.
- `/v1/providers` as a resource, and `provider` as an ordinary request field — a
  provider is a property of a device or a result (provenance), nothing more. *(review:
  the selection knob was removed from the v1 action request; §8.)*
- `/v1/devices/{id}/battery`, `/v1/devices/{id}/status` as GET resources — these are
  *operations* on the device (they run a command on the phone), not observed state.
  Reading them is `POST …/actions {"action": "battery.read"}`. The observed battery is
  in `/state` for free.
- `/state` as a top-level resource — `GET /v1/devices` already embeds each device's state;
  the snapshot file `state.json` remains for non-HTTP readers.
- `DELETE /v1/jobs/{id}` for cancel (the invariants' sketch) — a job record is history and is
  never deleted; DELETE would lie. `POST /v1/jobs/{id}/cancel` names the action and leaves
  the record in `cancelled` (§10).

Base URL example: `http://127.0.0.1:8741`. All bodies are `application/json; charset=utf-8`
unless noted. Every request needs `Authorization: Bearer <token>` (§16). Scope names are
defined in §17.

| Method | Path | Scope | Success | Slice |
|---|---|---|---|---|

| GET | `/v1/devices` | `device.read` | 200 `{"devices": [Device…]}` | 1 |
| GET | `/v1/devices/{device_id}` | `device.read` | 200 Device | 1 |
| GET | `/v1/devices/{device_id}/state` | `device.state.read` | 200 DeviceState | 1 |
| GET | `/v1/devices/{device_id}/capabilities` | `device.read` | 200 capabilities object | 1 |
| POST | `/v1/devices/{device_id}/actions` | the action's own name | 200 Result · 202 Job (+ `Location`) | 1 |
| GET | `/v1/jobs` | `jobs.read` | 200 `{"jobs": [Job…]}` | 1 |
| GET | `/v1/jobs/{job_id}` | `jobs.read` | 200 Job | 1 |

| GET | `/v1/events` | `events.read` | 200 `{"events": [Event…], "last_seq": N}` | 1 |
| GET | `/v1/events/stream` | `events.read` | 200 `text/event-stream` — canonical Events only | 1 |

Not exposed, deliberately: `daemon stop` (CLI over the socket only), `daemon install`,
pairing, profile editing, rule editing, any `run`/shell action, dependency installation
(`install: true` on any request is rejected).

Query parameters use the existing filter vocabulary: `type` (repeatable), `device`
(repeatable; canonical id or alias), `after` (seq), `since` (ISO timestamp), `limit`,
`state`, `action`, `rule`, `job_id`, `correlation_id`, `kind`. Never a token (§12.3).

## 6. Device schema

A **projection** composed from two existing records, not a new model: the registry
(`profiles.DeviceProfile` from `config.json`, via `cli.profile_identities`) and observed
state (`core.state.DeviceState` from the daemon's `Observer.states`). `models.Device`
(discovery) is *not* used here: it is produced by a live probe (`adb devices -l` +
`status` per device) and is the shape of `linkplane devices --json`, which stays as is.

### 6.2 `device_id` in every device-associated projection *(Slice 2)*

Jobs, events (history and stream), audit entries, and rules carry an added `device_id`,
resolved at read time from the record's registry name through the same resolver as
`GET /v1/devices/{id}`. It is **null** when the name no longer resolves (a profile renamed
or removed since the record was written, the observer's `*`) — never guessed. The pinned
`device` field stays as written; nothing persisted changes. Filters (`device=`) accept the
canonical id or an alias and are resolved to names before matching.

### 6.1 Canonical identity *(review)*

The canonical, rename-proof identity of a Device is **`device_id`** — the existing
`DeviceProfile.device_id`. Inspection: it is required on every profile
(`profiles_from_config` rejects a profile without one), it is the hardware serial recorded
at pairing (`pair_usb_device` / `pair_wireless_device` take it from ADB; `pair_ssh_device`
takes `--device-id` or the ADB serial), it is unique across profiles (an ADB or SSH
endpoint may belong to only one `device_id`), and it survives a rename
(`paired_device_id` keeps the existing id when a profile is re-paired under a new name).
No UUID registry is needed. For an unpaired observed device (`serial:<x>`) the
`device_id` is the serial itself.

The profile **name** is an alias. `GET /v1/devices/{id}` resolves, in order: a canonical
`device_id`, a profile name, `serial:<x>`. The resource always returns `device_id` as the
identity a client should store; `name` may change. Every `device` filter and every
`device` field the API *accepts* takes canonical id or alias; every `device` field the API
*returns* inside a pinned record (`Event.device`, `DeviceState.device`,
`JobRecord.device`, audit `device`) keeps what those records carry today — the registry
name — because those wire shapes are pinned. The projection therefore always shows both,
and `Device.name` is the join key into those records. Moving the observer, rules, and
history to key on `device_id` would be a breaking change to `automations.json`
(`device: phone`) and to history continuity; it is deferred (§25), and the API is designed
so that change is invisible to clients when it happens (`name` would then equal
`device_id` in old records only).

```json
{
  "device_id": "DEVICE_SERIAL",
  "name": "phone",
  "observed": true,
  "connection": "connected",
  "provider": "adb",
  "address": "DEVICE_SERIAL",
  "last_seen": "2026-09-11T09:14:02-05:00",
  "providers": [
    {"provider": "adb", "address": "DEVICE_SERIAL", "observed": true},
    {"provider": "ssh", "address": "u0_a123@192.0.2.229:8022", "observed": false}
  ],
  "state": {
    "device": "phone",
    "provider": "adb",
    "connection": "connected",
    "address": "DEVICE_SERIAL",
    "battery": {"level": 96, "status": "charging", "health": "good", "powered_by": ["usb"],
                "provider": "adb", "temperature_c": 31.1, "voltage_mv": 4245},
    "wifi_ssid": "HomeNet",
    "last_seen": "2026-09-11T09:14:02-05:00",
    "updated": "2026-09-11T09:14:02-05:00"
  }
}
```

| Field | Source | Notes |
|---|---|---|
| `device_id` | `DeviceProfile.device_id`; for an unpaired observed device, the serial | **canonical**, stable across renames; the id to store and the id in `Location` headers |
| `name` | registry name: `DeviceProfile.name`, or `serial:<x>` (`Observer.device_name`) | alias, accepted anywhere an id is; the value pinned records carry in their `device` field |
| `observed` | `id in Observer.states` | SSH-only devices are `false` (known limitation) |
| `connection` / `provider` / `address` / `last_seen` | `DeviceState` | absent (`null`) when not observed |
| `providers[]` | `DeviceProfile.adb_serials` (+ `preferred_adb_serial` first) and `DeviceProfile.ssh` (`user@host:port` only) | **never** `identity_file` or any key material |
| `state` | `DeviceState.to_dict()` verbatim | same object as `GET …/state` |

`manufacturer`/`model`/`android` are **not** in the projection: `DeviceState` does not carry
them, and the API must not probe the phone on a GET. They are available through the
`device.status` action (a `StatusResult`). If the observer later records the tracker's
`model`/`product` in `DeviceState` (additive), the projection gains them for free.

## 7. Capability schema

`GET /v1/devices/{id}/capabilities` runs `Provider.capabilities()` for each provider the
device has (the same call `linkplane capabilities` makes; ADB: `select_device` + the scrcpy
check; SSH: one `probe_ssh_endpoint`). `?provider=adb|ssh` restricts it.

```json
{
  "device": "phone",
  "queried": "2026-09-11T09:15:00-05:00",
  "capabilities": [
    {"name": "battery.read",   "status": "supported",   "provider": "adb", "detail": "ADB shell",
     "requirements": [], "metadata": {}, "granted": true},
    {"name": "clipboard.read", "status": "supported",   "provider": "ssh", "detail": "Termux:API (termux-clipboard-get)",
     "requirements": [], "metadata": {}, "granted": false},
    {"name": "screen.control", "status": "unavailable", "provider": "adb", "detail": "scrcpy is not installed on this computer",
     "requirements": ["D"], "metadata": {}, "granted": false},
    {"name": "camera.capture", "status": "unavailable", "provider": "ssh", "detail": "termux-camera-photo is not installed on the phone",
     "requirements": [], "metadata": {}, "granted": false}
  ],
  "by_provider": {
    "adb": [ {"name": "device.ping", "status": "supported", "detail": "ADB shell", "requirements": [], "metadata": {}}, "…" ],
    "ssh": [ "…" ]
  }
}
```

- `by_provider.<name>[]` is `CapabilityReport.to_dict()` verbatim, one per catalogue entry,
  in catalogue order — exactly `linkplane capabilities --json`'s `capabilities` list.
- `capabilities[]` is the **effective** list: for each catalogue name, the report from the
  first provider in `auto` order (ADB, then SSH — `providers.select_provider`) whose status
  is `supported`; otherwise the ADB report (or the only provider's). It adds `provider`.
  This is the same choice `auto` makes at action time, so "effective" is not invented.
- `granted` is **authorization metadata about the calling client** (its scopes, §17), not
  device state. It is the only API-layer annotation, and it exists so a GUI can grey out a
  button for the right reason.

What the five statuses answer today versus the brief's future vocabulary:

| Brief concept | Today | Notes |
|---|---|---|
| supported / available | `supported` | the catalogue does not distinguish "could" from "can now": `supported` means usable now |
| temporarily unavailable | `unavailable` (+ `detail`) | e.g. scrcpy missing, script missing, device disconnected (ADB provider reports this) |
| permission required | `permission-denied` | ADB unauthorized (`LP-AUTH-002`), Termux:API grant missing |
| consent required | `granted: false` | client-scope level only; per-action approval gates are deferred |
| provider missing | `unsupported` on that provider; absent from `by_provider` if the device has no such provider | a device-level "no provider can do this" is derivable: every `by_provider` entry `unsupported` |
| device disconnected | `unavailable` with the classify message | a dedicated status is **reserved**; adding one is an append to `STATUSES` |

## 8. Action request schema

One request shape for every action. Action identifiers are **capability names** from
`core.capability.CATALOGUE` (plus two additive catalogue entries this design needs, §8.2).

```json
POST /v1/devices/DEVICE_SERIAL/actions
Authorization: Bearer …
Content-Type: application/json

{
  "action": "notify.post",
  "parameters": {"message": "Build 291 passed", "title": "CI"},
  "correlation_id": "ci-291"
}
```

| Field | Required | Meaning |
|---|---|---|
| `action` | yes | capability name; a name outside the catalogue → 400 `LP-REQUEST-001`; a catalogue name with no API execution entry → 501 (§15) |
| `parameters` | no (default `{}`) | maps **one-to-one onto the service's `Request` dataclass fields** (table below); unknown keys, wrong types, or a seam field → 400 `LP-REQUEST-001` |
| `correlation_id` | no | opaque string ≤ 128 chars supplied by the caller; else the server assigns `core.events.new_id()`; echoed in the Result, the Job, and every audit entry |

The target device is the URL, never a body field. The client identity comes from the
token, never from the body. There is no `dry_run` at the top level: it is a field of the
requests that have it and is passed through as such.

**No `provider` in the request** *(review)*. Linkplane chooses the provider from the
device's providers, their capability status, and the existing `auto` order (ADB first,
SSH fallback — `providers.select_provider`). The chosen provider appears in the Result
and the Job (provenance) and in the audit entry, never as an input. *Capability ≠
implementation.* A developer-only override (for diagnosis) is reserved as a
non-contract, feature-flagged field and is not part of `linkplane.api/1`.

names only".

`serial_from_profile`, `config_path`, `state_path`, `install`, `foreground`,
`extra_arguments`, and every `*_factory` / `*_runner` keyword. `SendRequest.transport =
"localsend"` is not reachable (it hands the batch to an external GUI process).

### 8.2 Validation order (deterministic)

1. authenticate the token → 401 `LP-CLIENT-001`
2. parse body, `action` known → 400 `LP-REQUEST-001`
3. scope granted for `action` → 403 `LP-CLIENT-002` (audited `action.blocked`)
4. device exists in the registry → 404 `LP-CONFIG-003`
5. `parameters` build the `Request` dataclass → 400 `LP-REQUEST-001`
6. provider resolution (`select_provider` semantics, `auto` only) → 503 `LP-CONNECT-*` / 500 `LP-CONFIG-001`
7. capability status for the resolved provider is `supported` → 409 `LP-CAPABILITY-001` (this device cannot do it) / 409 `LP-CAPABILITY-002` (not right now) / 503 `LP-AUTH-002` (permission-denied)
8. run per the action's declared execution mode (§9): immediate → 200 Result; job → 202 Job

Step 7 is the capability check the invariants require; it uses the same
`Provider.capabilities()` the GET uses, so a client that just listed capabilities sees
the same answer the action gives.

## 9. Immediate result vs job semantics

**Rule *(review)*: execution mode is declarative.** Each API action has an explicit
metadata entry — `ActionSpec(name, execution, request_type, job_action, providers,
parameters)` in one table — and `execution ∈ {"immediate", "job"}` is read from it:

```text
action in JOB_ACTIONS (declared)  →  asynchronous Job   (202)
otherwise                         →  immediate Result   (200)
```

The initial membership is derived from today's behaviour (`actions.JOB_ACTIONS`:
`backup`, `send`, `clipboard-sync`, i.e. the services that take `cancel=` and report
progress), but the contract is the table, **not** the function signature: a later refactor
of a service's keyword arguments cannot change an action's HTTP behaviour. Changing an
action's execution mode is a breaking API change. The kind is never decided per request or
by elapsed time.

```text
POST /v1/devices/{id}/actions
     │
     ├── immediate ──► service runs on the request thread ──► 200  Result   (or 4xx/5xx error)
     │
     └── job ────────► JobRunner.run(...) on a small API executor (max 4, separate from
                       │  the rule firing pool so client jobs never delay rule firings)
                         └─ record written (state: running) ──► 202  Job + Location: /v1/jobs/{id}
```

How a caller tells: **the status code** (200 vs 202) and **the body's shape** (a Result has
`value`; a Job has `state`). Both are always true together; clients may switch on either.

A job's outcome is read from `GET /v1/jobs/{id}` or the stream (§12); its `result` is the
same `to_dict()` the immediate path would have returned as `value`. A duplicate job
request (same device + job action already running) is recorded by the runner as `skipped`
and returned as **409 `LP-STATE-001`** with `details.job_id` naming the skipped record —
the runner's behaviour, not a second check.

Immediate actions run with the services' own timeouts (provider `timeout=8`,
`find.duration`, …); a `timed out` failure classifies to `LP-TIMEOUT-001` → 504. The
handler adds no timeout of its own in slice 1.

### 9.1 Result representation

A projection of `OperationResult` provenance fields (`operation → action`, `resource_id →
device`, `provider`, `warnings`, `value`) using the **same field names `JobRecord` uses**,
so a Result and a Job read alike:

```json
{
  "action": "battery.read",
  "device": "phone",
  "provider": "adb",
  "actor": "client:waybar",
  "correlation_id": "6f1c0e6f4a1d4a0aa1c6c3e2d5b7f8a9",
  "started": "2026-09-11T09:16:00-05:00",
  "finished": "2026-09-11T09:16:00-05:00",
  "value": {"level": 96, "status": "charging", "health": "good", "powered_by": ["usb"],
            "provider": "adb", "temperature_c": 31.1, "voltage_mv": 4245},
  "warnings": []
}
```

`value` is the service result's `to_dict()` unchanged (`BatteryReading`, `PingResult`,
`StatusResult`, `NotificationResult`, `FindPhoneResult`, `ClipboardResult`, …). Partial
telemetry stays a success with `issues` inside `value` — the providers' contract. The
frozen `transport` key inside those results is left as is (preferred term documented:
`provider`).

## 10. Job representation

### 10.1 Public action identity *(Slice 2)*

A client requests `backup.photos`; the runner records `backup` (the rules/jobs
vocabulary, which duplicate detection and `automations.json` depend on). The public
representation does not require clients to know both: `action` is the **public
capability name**, and the record's own name is exposed as `job_action`:

```text
API action:           backup.photos     files.send     clipboard.sync
internal job action:  backup            send           clipboard-sync
```

The mapping is `api.actions.PUBLIC_ACTIONS` (the inverse of the declared `JOB_ACTIONS`),
pinned in `docs/openapi.json` (`x-public-actions`). `GET /v1/jobs?action=` and
`GET /v1/audit?action=` accept either name; audit entries whose `action` is a job action
are projected the same way (`action` public, `job_action` original). The persisted
`JobRecord` is unchanged.

`JobRecord.to_dict()` **verbatim**, plus the `rule` alias (`Firing.to_dict()` precedent),
the additive field `actor`, and the Slice 2 projection keys `action` (public),
`job_action`, and `device_id`:

```json
{
  "id": "20260911T091700-0500-client-waybar-backup-3",
  "automation": "",
  "rule": null,
  "actor": "client:waybar",
  "action": "backup.photos",
  "job_action": "backup",
  "device_id": "DEVICE_SERIAL",
  "device": "phone",
  "state": "running",
  "started": "2026-09-11T09:17:00-05:00",
  "finished": null,
  "attempt": 1,
  "progress": {"phase": "item_completed", "message": "IMG_2041.jpg", "current": 12, "total": 40, "unit": "files"},
  "result": null,
  "error": null,
  "correlation_id": "6f1c0e6f4a1d4a0aa1c6c3e2d5b7f8a9"
}
```

- States are exactly `running · retrying · completed · failed · cancelled · skipped`; no
  rename, no `queued`. `attempt` counts; `correlation_id` never changes across retries.
- `action` is the **job action name** (`backup`, `send`, `clipboard-sync`) because the
  runner's duplicate detection keys on it and rules already use it. The capability that
  requested it is recoverable from the audit entry (`action.requested`, §22) and from
  §8.1's mapping. (`JobRunner._new_id` builds the id from `automation` and `action`; for
  an API job, whose `automation` is empty, it uses the actor instead — hence
  `…-client-waybar-backup-3` above. Implementation detail of the additive `actor` field.)
- `rule` is `null` and `automation` is `""` for API-originated jobs; both are the rule
  name for rule-originated jobs. Additive: `JobRecord.actor: str | None = None`
  (`rule:<name>` written by the daemon for rule jobs, `client:<id>` for API jobs) so
  `AuditWriter.job()` can stop deriving the actor from `automation`.
- `GET /v1/jobs` is `read_jobs()` newest first, filtered by `device`, `action`, `state`,
  `rule`, `correlation_id`; `limit` default 50, max 500 (§21).

**Cancellation** (`POST /v1/jobs/{id}/cancel`, scope `jobs.cancel`, no body) uses
`JobRunner.cancel(job_id, reason)`; nothing HTTP-specific decides anything. Pinned
semantics, per record state:

| Record state | Response | Audit (`job.cancel`, actor `client:<id>`, source `api`) |
|---|---|---|
| `running` / `retrying`, running in this daemon | **202** + the record as it stands; it reaches `cancelled` at its next boundary (reason `cancelled by client:<id>`), observable on `GET` | `started`, then the runner's own `job.cancelled` |
| `cancelled` | **200** + the record (idempotent) | `skipped` |
| `completed` / `failed` / `skipped` | **409** `LP-STATE-001`, `details.state` | `blocked` |
| `running` on disk but not running here (stale record from a crashed run) | **409** `LP-STATE-001`, `details.stale: true` | `blocked` |
| unknown id | **404** `LP-RESOURCE-001` | — |
| any body | **400** `LP-REQUEST-001` | — |

No `cancelling` state is invented: the runner has none, and the record's `state` tells
the truth at every moment. Evaluated `DELETE /v1/jobs/{id}`: rejected (§4).

## 12. Streaming design

### 12.1 Decision: Server-Sent Events on the same HTTP listener

| Criterion | SSE | WebSocket | Raw socket stream exposed |
|---|---|---|---|
| Matches the existing model (one request, then one-way records until close) | exactly | more than needed | exactly, but not HTTP |
| Resume | built in (`Last-Event-ID`) | must be designed | must be designed |
| Browser / GUI / SDK support | `EventSource` everywhere; `curl` works | needs a library in stdlib Python (none) | needs a Unix-socket client |
| Stdlib server | plain `http.server` write loop | hand-written framing + masking + ping/pong (RFC 6455) | already exists |
| Filters | query string at connect (as `subscribe {types, devices}` today) | could change mid-stream — nothing needs that | at connect |
| Bidirectional need in the repository | none found | — | — |

**Nothing in the repository sends a client→server message after subscribing.** Actions are
request/response (`POST`), and cancellation is `POST`. SSE is therefore the smallest
transport that exposes the canonical stream correctly. WebSocket is reserved for a future
need that actually requires bidirectional realtime (none identified); it would be an
additional transport over the same `Subscriber`, not a replacement.

### 12.2 Wire format

`GET /v1/events/stream?after=1042&type=battery.low&type=battery.ok&device=phone`

```text
HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache
Connection: keep-alive

retry: 2000

event: stream
data: {"protocol": "linkplane.api/1", "last_seq": 1042, "resumed_after": 1042, "gap": false}

id: 1043
event: event
data: {"schema":"linkplane.event/1","type":"battery.low","device":"phone",…,"seq":1043,…}

: keepalive

id: 1044
event: event
data: {…}
```

- `event: event` — an `Event` (`Event.to_dict()`); `id:` is its `seq`. **This is the only
  record type on the stream** *(review, D4)*: `/v1/events/stream` carries canonical Events
  and nothing else. Job records, audit entries, and rule activity have different
  identities and lifecycles (`JobRecord.id`, `audit_id`, no `seq`) and multiplexing them
  here would break the one-cursor continuation model. Live job updates, if wanted later,
  get their own `/v1/jobs/stream` or a dedicated multi-resource subscription protocol.
  *A transport notification is not automatically a Linkplane Event.*
- `event: stream` — the **only HTTP-specific message**, sent once at connect: transport
  metadata a client needs to reason about resume (`last_seq` at connect, what it resumed
  after, whether a gap exists). It is not a Linkplane event and never enters history.
- `: keepalive` comment every 15 s so idle proxies and clients detect a dead daemon.
- Daemon stop closes every stream after the `observer.stopped` event (the daemon offers
  `None` to each subscriber today); clients reconnect with `Last-Event-ID` and get
  `LP-DAEMON-001`-equivalent connection refusal until it is back.

Server-side, a stream is one `Subscriber(types, devices)` added to the daemon exactly like a
socket subscriber (bounded queue; drops on slow clients with a warning — a dropped event is
visible to the client as a `seq` jump, and recoverable from `GET /v1/events?after=`).

### 12.3 Authenticating the stream *(review)*

The stream is authenticated exactly like every other request: `Authorization: Bearer …`.
**A token never appears in a URL** (`?token=` is rejected with 400 and never echoed),
never in a cookie, and never in a log line.

- Native, desktop, CLI, SDK, and MCP clients send the header on an ordinary HTTP request
  and read the body as it streams (Python `http.client` / `urllib`, `curl -N`, Go, Rust,
  Node all do this).
- Browser-based clients (a webview GUI, developer tooling) **do not use native
  `EventSource`** in v1, because it cannot set an `Authorization` header. They use
  `fetch()` with the header and consume `response.body` as a `ReadableStream`, parsing
  the SSE frames (`id:` / `event:` / `data:` / blank line). Reconnect-with-`Last-Event-ID`
  is then the client's own loop, using the last `id:` it parsed — identical semantics.
- A short-lived, single-use *stream credential* that would make native `EventSource`
  usable is **reserved, not designed now**.

## 13. Resume semantics

- **`seq` is authoritative** for continuation; `event_id` is not ordered and is never used
  as a cursor. There is no new cursor type.
- **Where the cursor goes:** the SSE `Last-Event-ID` header (what `EventSource` sends on
  its own reconnect) or the `after` query parameter. If both are present, `after` wins
  (explicit beats automatic). Both mean "events with `seq > N`".
- **Replay then live, no duplicates within a connection:** on connect the server adds the
  subscriber (so nothing is missed), reads history `seq > N` (`history.read_history`),
  writes those, then drains the live queue skipping anything with `seq ≤` the last one
  replayed. Within one connection every `seq` is delivered at most once, in increasing
  order. Across reconnects a client that persisted `N` never receives `seq ≤ N` again; a
  client that lost its cursor may see duplicates — de-duplicate by `seq`.
- **Ordering:** by `seq`, which is write order in the daemon (single `HistoryWriter`).
  `ts` is not an ordering key (second precision, host clock).
- **Ahead of history** (`after` > current `last_seq`, e.g. the history file was deleted and
  `seq` restarted): the `stream` message reports `gap: true` and the server streams live
  only. `GET /v1/events?after=` returns an empty page with `last_seq` so the client can see it.
- **Pruned history:** not implemented today (the file is append-only and never truncated).
  Reserved behaviour, so clients can code for it now: when a retention limit exists and
  `after` is below the oldest retained `seq`, the `stream` message carries `gap: true`
  and `oldest_seq`, replay starts at `oldest_seq`, and `GET /v1/events` includes `oldest_seq`.
  No error is raised: a gap is information, not a failure.
- **Initial-state events:** none are synthesized for a new stream. `initial` events exist
  in the canonical stream only where the observer emits them (start-up, reconnect). A
  client that wants current state reads `GET /v1/devices` (observed state) and then streams
  from the `last_seq` reported by `GET /v1/health` (or the `stream` message); a state read
  that lands slightly after `last_seq` merely means the client also receives the event
  that produced it — harmless, because state reads are idempotent.
- **No daemon history** (`daemon run --no-history`): events have `seq: null`; the stream
  is live-only and the `stream` message says `last_seq: null`; `after` is rejected with
  400 `LP-REQUEST-001` ("history disabled").

## 14. Error response schema

The body is `LinkplaneError.to_dict()` under one `error` key (the CLI envelope's key), plus
two additive fields:

```json
HTTP/1.1 503 Service Unavailable
Content-Type: application/json; charset=utf-8

{
  "error": {
    "type": "LinkplaneError",
    "code": "LP-CONNECT-002",
    "message": "no ADB device connected",
    "hints": ["the phone is plugged in or wireless debugging is connected",
              "USB debugging is enabled and this computer is authorized"],
    "correlation_id": "6f1c0e6f4a1d4a0aa1c6c3e2d5b7f8a9",
    "details": {}
  }
}
```

- `type`, `code`, `message`, `hints` exactly as `core.errors` produces them; a plain
  `BridgeError` from a service is wrapped by `errors.classify()` first; an
  `OperationError` is mapped through `errors.OPERATION_CODE_MAP` (its `error_code`/`hints`
  used when set).
- `correlation_id` is always present (the request's or the server-assigned one).
- `details` is an optional object for structured context (`{"job_id": …}` on 409,
  `{"scope": …}` on 403, `{"parameter": …}` on 400). Never stack traces, never paths to
  keys.
- The HTTP status never replaces the code; clients switch on `code` and treat unknown
  codes as `LP-PROVIDER-001` (invariants).
- Unexpected exceptions become `LP-INTERNAL-001` (500) with the fixed message
  "internal error; see the daemon log" — never the Python exception text, subprocess
  output, provider stderr, or a filesystem path. The traceback goes to the daemon log only
  (§18).

## 15. LP error → HTTP status mapping

Established HTTP semantics, one table, deterministic. Codes marked **new** are additive
entries in `core/errors.py` (with titles; the pinned set may grow, never shrink).

| Condition (brief) | Code | HTTP | Rationale |

| no such route | `LP-REQUEST-001` | 404 | same code, `details.path` |
| wrong method | `LP-REQUEST-001` | 405 + `Allow` | |
| body not JSON / wrong content type / > 64 KiB | `LP-REQUEST-001` | 400 · 415 · 413 | |

| cancelled (immediate action interrupted by daemon stop) | `LP-CANCELLED-001` | 503 | the server is going away |
| configuration missing / invalid | `LP-CONFIG-001` / `-002` | 500 | server misconfigured; hints point at `linkplane doctor` |

| daemon not running / already running | `LP-DAEMON-001` / `-002` | — | cannot occur over HTTP (the API is the daemon); connection refused is the signal |
| internal failure | `LP-INTERNAL-001` **new** | 500 | |
| API listener could not bind | `LP-API-001` **new** | — (start-up log + audit `daemon.started` details) | not an HTTP response |

Success codes: 200 (resource, Result), 202 (Job created or cancel accepted), 204 is not
used (every success has a body).

## 16. Client identity model

Smallest model that answers *who requested this*, reusing the audit `actor` string.

```text
actor = "client:<client_id>"        (audit v2 `actor`; today: "daemon", "rule:<name>")
```

Registry file `~/.config/linkplane/clients.json` (mode 0600; `LINKPLANE_CLIENTS` override,
resolved through `paths.config_file`):

```json
{
  "schema": "linkplane.clients/1",
  "clients": [
    {
      "client_id": "waybar",
      "client_name": "Waybar battery module",
      "client_type": "tool",
      "scopes": ["device.read", "device.state.read", "events.read"],
      "token_sha256": "e3b0c442…",
      "created": "2026-09-11T09:00:00-05:00"
    }
  ]
}
```

| Field | Rule |
|---|---|
| `client_id` | slug `[a-z0-9][a-z0-9-]{0,31}`, unique; appears in `actor`, audit, job ids |
| `client_name` | free text for humans |
| `client_type` | `cli` · `gui` · `sdk` · `mcp` · `automation` · `agent` · `tool` (the brief's list; informational, no policy hangs on it yet) |
| `scopes` | explicit list (§17); nothing is implied |
| `token_sha256` | SHA-256 of the bearer token; the plaintext is shown once and written to `~/.config/linkplane/clients/<client_id>.token` (0600) so a same-user process can be pointed at the file — the "token file per client" the invariants anticipated |

**Provisioning is a Slice 0 deliverable** *(review)*; nobody edits `clients.json` by hand.
Following the `profiles list|remove|default` and `daemon install|uninstall` conventions:

```text
linkplane clients create <id> [--name TEXT] [--type TYPE] [--scope S ...] [--json]
linkplane clients list [--json]
linkplane clients revoke <id> [--json]
```

Requirements, all pinned by tests: the token is `secrets.token_urlsafe(32)` (256 bits of
entropy, machine-generated — so a plain SHA-256 digest is the right storage, unlike a
human password); the plaintext is displayed **once** on creation (and written to
`clients/<id>.token`, 0600, only with `--token-file`); only `token_sha256` is stored;
writes are atomic (temp file + `os.replace`) with mode 0600 on file and 0700 on the
directory; comparison is `hmac.compare_digest` on the digests; the token is never logged,
never audited, never echoed back after creation; scopes are an explicit list — no
wildcard, no `admin`; `revoke` removes by `client_id` and takes effect on the next
request (the daemon reloads the file on change: mtime check per request is cheap at this
size, plus `daemon reload`). Creating a client is the human consent step (§18); the CLI
prints the granted scopes back and names the sensitive ones. The daemon audits
`clients.loaded` (`decision: loaded`, count only — never ids of tokens).

Requests: `Authorization: Bearer <token>`. Token → `client_id`; compared in constant time
against the hash. `GET /v1/health` returns `client: {client_id, client_type, scopes}` so a
client can discover what it may do without a `/clients/me` route. Health carries nothing
else that is device- or configuration-specific (no paths, no device list): those are
`/v1/devices` and the CLI's `daemon status`.

The CLI is **not** an HTTP client in this milestone: it keeps calling services directly and
using the 0600 control socket (actor `daemon` / `rule:*`). A future `local-cli` client
identity can be added without changing anything here.

  else.

- `GET /v1/devices/{id}/capabilities` reports `granted` per capability from these scopes.

## 18. Consent and security behaviour

The existing consent boundary is: **a privileged action requires an explicit, persistent,
human-written grant** (a rule's `allow: ["run"]`, checked at load; never implied). The API
maps onto it without weakening it:

| Concern | Behaviour |
|---|---|
| Who consents | the local user, by running `linkplane clients add … --scope <sensitive>`; the CLI names sensitive scopes explicitly when granting them |
| Shell / script execution | no endpoint; `run` exists only inside rules loaded from the user's file; the API cannot create or edit rules (no `rules.write`), so it cannot smuggle a `run` rule; `shell.execute` is reserved and never grantable in this milestone |
| Camera / microphone / screen | `camera.capture` is a sensitive scope (slice 2); audio capture, camera preview, webcam, and screen are sessions and are deferred (§25) — not exposed at all |
| File access | `files.send` reads host files; `backup.photos` writes host files; both sensitive; paths are used exactly as the CLI would (user-expanded, no sandbox — same trust as the CLI running as that user) |
| Clipboard reading | `clipboard.read` and `clipboard.sync` are sensitive; `clipboard.write` is a lesser write |
| Destructive actions | none exist in the catalogue today (no delete/wipe/install); when one is added it is sensitive by default |
| Persistent automation creation | not exposed; the rules file stays the source (`docs/adr/0009`) |
| Dependency installation | `install: true` is rejected on every request (400) — the API never runs a package manager |
| Every action is audited | `action.requested` → `action.completed` / `action.failed` / `action.blocked` with `actor: client:<id>`, `source: "api"`, `correlation_id`, the action name, the device, and the capability status observed; job actions are audited by the existing transition hook with the client actor |
| Errors leak nothing | messages are the same the CLI prints; no key paths, no tokens, no stack traces |
| Request limits | body ≤ 64 KiB, header defaults of `http.server`, socket timeout 30 s on request lines; SSE connections are unlimited in time but bounded in count by a soft cap (64) after which 503 `LP-STATE-001` |
| Token handling | compared by SHA-256 in constant time; never logged; never audited; `clients.json` is 0600 |

Per-action human approval gates (vision §22, "Allow once") are **deferred**; the code
`LP-CONSENT-001` is reserved for them so clients can distinguish "you need a scope" from
"a human must approve this one" without a shape change.

### 18.1 Sensitive-data logging rules *(review)*

The HTTP layer's operational log (`logging`, `linkplane.api`) follows the output-channel
rules in `docs/current-state.md` and adds:

| Never logged, at any level | Logged (INFO / DEBUG) |
|---|---|
| `Authorization` header or any bearer token (also not in `--debug`) | method, path, status, duration, `client_id`, `correlation_id` |
| clipboard contents; file contents; camera/audio payloads | action name, device id, execution mode, `LP-` code on failure |
| raw request bodies (by default; `--debug` logs the *shape*: keys and value types) | the daemon's usual WARNING lines |
| sensitive action parameters: `text` (clipboard), `message` (notify — truncated to 40 chars at DEBUG), host `paths`/`destination` beyond the basename | |

Error responses never contain Python exception strings, subprocess output, provider
stderr, or local filesystem details (§14); those go to the operational log only, at
WARNING with the correlation id so a support conversation can join the two. A pinned
test greps a captured log of a full request cycle (including a failing one) for the
token and the clipboard text.

### 18.2 The HTTP layer is a transport adapter *(review, D1)*

It contains **no business logic**: no provider selection rules of its own, no retry, no
duplicate detection, no consent decision beyond "is the scope granted". It parses,
authenticates, authorizes, resolves ids through the shared registry, calls the same
services and `JobRunner` everything else calls, and renders. A listener failure (bind
error, handler crash, a thread dying) is logged and audited and **never** stops the
observer, rules, jobs, history, or the control socket; the daemon's `describe()` reports
`api: null` and keeps running.

## 19. Binding and network defaults

| Question | Decision |
|---|---|
| Default bind | `127.0.0.1` (IPv4 loopback) TCP only. `::1` is accepted as a configured value (still loopback); a dual-stack default is reserved |
| Default port | `8741` (unassigned in this host's `/etc/services`; founder may pick another) |
| Configuration | `config.json` `"api": {"enabled": true, "bind": "127.0.0.1", "port": 8741}`; CLI `daemon run [--api-bind ADDR] [--api-port N] [--no-api]`; `daemon install` passes the same flags into the unit; `LINKPLANE_API_BIND` / `LINKPLANE_API_PORT` overrides via `paths.env` |
| Discovery | the daemon writes `$XDG_RUNTIME_DIR/linkplane/api.json` (0600) `{"url": "http://127.0.0.1:8741", "pid": …, "protocol": "linkplane.api/1"}` next to `daemon.sock`, and `daemon status` reports it; an SDK reads the file instead of hard-coding the port |
| Collision | the API listener fails to bind → the **daemon keeps running** (observing, rules, jobs, socket), logs and audits `LP-API-001` with the address, `daemon status` shows `api: null`. `--api-port 0` asks the OS for a free port (written to `api.json`). Nothing retries other ports silently. |
| Unix-socket HTTP | not in slice 1. Evaluated: better same-user isolation, but browsers cannot reach it, `EventSource` cannot, and it complicates every SDK; the bearer token closes the multi-user loopback gap. Reserved as a second listener (`"api": {"socket": "…"}`) if a founder decision (§26 D2) prefers it. |
| Remote binding | **does not exist in this milestone.** A request to bind anything that is not a loopback address (`0.0.0.0`, `::`, a LAN address) is refused at start-up with `LP-REQUEST-001` and the message "remote binding is not supported in this version; the API is local-only" — the daemon still starts, without the API. No `--i-know-what-i-am-doing` flag. |
| TLS | none (loopback only) |
| Origin / CORS *(review)* | a loopback address is **not** an authorization boundary against a browser: any web page the user opens can issue requests to `127.0.0.1`. Therefore: no `Access-Control-*` headers are ever emitted (no CORS grant), **and** any request carrying an `Origin` header that is not in the configured allow-list (`"api": {"allowed_origins": []}`, empty by default) is refused with 403 `LP-CLIENT-001` before authentication is even attempted. Browser preflights (`OPTIONS`) get 403. A future webview GUI either sends no `Origin` (native fetch) or is added to the allow-list explicitly. |
| Host validation *(review)* | the `Host` header must be `127.0.0.1[:port]`, `localhost[:port]`, or `[::1][:port]` matching the bound port; anything else (DNS-rebinding style names) is refused with 403 `LP-CLIENT-001`. |
| Cookies | never read, never set; authentication is the bearer header only |

## 20. Versioning strategy

Existing policy (`docs/versioning.md`): milestone tags `core-vX.Y`, package SemVer
`0.MINOR.PATCH`, public release tags `vX.Y.Z`; `CONTRACT_VERSION` and `schema_version`
independent; every record has its own `schema` tag (`linkplane.event/1`, `linkplane.audit/2`,
`linkplane.state/1`, `linkplane.daemon/1`).

**Decision *(review, D3)*: every path carries the API major, `/v1/…`.** The API major is
an *interface-compatibility* version and answers a different question from the package
version (`0.3.0`, "what is installed"), the milestone tags (`core-v0.x`, `api-v0.x`,
"which architectural section is complete"), and the record schemas (`linkplane.event/1`,
"how to read this line"). It is cheaper to carry the explicit major now than to retrofit
it after SDKs and third-party clients exist.

- `GET /v1/health` also reports `"api": "linkplane.api/1"` and every response carries
  `Linkplane-Api: 1`; the two numbers are the same number (the path is the primary
  signal; the tag lets a client verify what answered).
- Compatibility rules for `/v1`: additive fields, new actions, new scopes, new codes, new
  event types, and new query parameters are non-breaking (clients ignore unknown keys).
  Renaming or removing a field or route, changing an action's execution mode, changing a
  status mapping, or changing an existing code's meaning requires `/v2`, which may be
  served side by side with `/v1` for a deprecation period.
- `docs/versioning.md` gains one row for the API major. The milestone tag when the API
  ships is `api-v0.1`; the package `MINOR` increments in the commit that finishes the
  section.

## 21. Pagination and history behaviour

No offset/cursor machinery; the existing identifiers are the cursors.

| Resource | Ordering | Continuation | Default / max `limit` | Filters | Time filter |
|---|---|---|---|---|---|
| `GET /v1/events` | ascending `seq` (default) or `order=desc` | `after=<seq>` (asc) · `before=<seq>` (desc) | 100 / 1000 | `type` (repeatable), `device` (repeatable), `correlation_id` | `since=<ISO ts>` — justified: `events` history is the only long file and "what happened since 9:00" is a real GUI/agent question; `ts` is not an ordering key, so `since` is a filter, not a cursor |
| `GET /v1/jobs` | newest first (`started`) | `before=<job_id>` reserved; today `limit` is a tail like `automations jobs -n` | 50 / 500 | `device`, `action`, `state`, `rule`, `correlation_id` | none |
| `GET /v1/audit` | newest first (`ts`) | `before=<audit_id>` reserved (ids are unordered; the reader walks the file) | 100 / 1000 | `device`, `rule`, `job_id`, `action`, `kind`, `actor`, `correlation_id` | `since=<ISO ts>` |

Collection bodies follow the CLI's JSON precedent (`{"jobs": [...]}`, `{"capabilities":
[...]}`): `{"events": [...], "last_seq": N}`, `{"jobs": [...]}`, `{"entries": [...]}`.
`last_seq` on events is the newest sequence in history at query time, so a client knows
whether it has caught up. `oldest_seq` appears once pruning exists (§13).

Implementation reality: `read_history`, `read_jobs`, `read_audit` scan whole files. Fine at
today's sizes (thousands of lines); an index is reserved for when a file is large enough
to matter, and would not change the contract.

## 21.1 Rules exposure *(Slice 2)*

`GET /v1/rules` (`rules.read`, sensitive: not in the `read` default) projects the daemon's
**loaded** rule set — `Daemon.rules` (`LoadedRules`, active and blocked) — never a second
store and never the filesystem path. Per rule: `name`, `state` (`active` | `blocked`),
`enabled`, `when`, `device` + `device_id`, `if`, `cooldown_seconds`, `on_initial`,
`continue_on_error`, `allow`, `blocked_actions`, `do[]`. Steps carry their options (with
`capability` for job actions), except **`run` steps, whose command text is intentionally
omitted** (`"command": "[redacted]"`, `privileged: true`, `timeout`): a command line can
embed credentials or paths the operator never meant to publish, and inspection needs
only to know that a rule runs a command. `POST /v1/rules/reload` (`rules.reload`) takes
**no body** — a body of any shape is 400 — and reloads the file the daemon was started
with (`Daemon.reload_rules()`); a broken file is 500 `LP-CONFIG-002` and the previous
rules stay in force. Returns `{loaded, active, blocked, fired}`. Audited as `rules.reload`
(`loaded` / `error`) with the client actor, beside the daemon's own `rules.loaded`.

## 22. Audit exposure

`GET /v1/audit` returns audit lines **as written** (`linkplane.audit/2`; v1 lines are passed
through as the reader loads them). No API-specific audit schema.

```json
{
  "schema": "linkplane.audit/2",
  "audit_id": "b1d2…",
  "ts": "2026-09-11T09:17:00-05:00",
  "kind": "action.requested",
  "actor": "client:waybar",
  "source": "api",
  "decision": "started",
  "device": "phone",
  "job_id": "20260911T091700-0500-…",
  "action": "backup.photos",
  "correlation_id": "6f1c…",
  "details": {"provider": "adb", "capability_status": "supported", "job_action": "backup", "parameters": {"source": "/sdcard/DCIM/Camera", "destination": "~/Pictures/Phone"}}
}
```

| Brief field | Actual | Notes |
|---|---|---|
| `audit_id` · `timestamp` · `actor` · `source` · `device_id` · `rule_id` · `job_id` · `action` · `decision` · `correlation_id` · `details` | `audit_id` · `ts` · `actor` · `source` · `device` · `rule` · `job_id` · `action` · `decision` · `correlation_id` · `details` | `kind` is the entry type; `result` lives in `details.result` for jobs |

New kinds written by the API (open vocabulary; `decision` stays closed): `action.requested`
(`started`), `action.completed` (`completed`), `action.failed` (`failed`), `action.blocked`
(`blocked` — scope or capability refusal), `clients.loaded` (`loaded`). `source` is `"api"`
for these — additive `source=` keyword on `AuditWriter.write()` so one writer (one file
handle, no interleaving) serves both the daemon and the API. Parameters are audited with
secrets impossible by construction (there are none in any `Request`) but **clipboard text
is never audited** (`clipboard.write` records `{"text_length": n}`) and `notify.post`
message text is truncated to 200 chars.

Privacy: the audit log contains event data (SSIDs, battery), rule outcomes including the
last 2000 bytes of `run` command stdout, job results with file names, and action
parameters (host paths). Therefore `audit.read` is a **sensitive scope**, not part of the
`read` shorthand, and a client's own actions are not readable without it (no "my entries"
carve-out in this milestone — reserved: `GET /v1/audit?actor=client:me` could be allowed under
`jobs.read` later if a founder wants it).

**HTTP projection *(Slice 2)*.** `GET /v1/audit` (`audit.read`) never mutates the log and
never returns it raw. Each entry passes through `api.security.redact_record`: any key in
`SENSITIVE_KEYS` (`text`, `command`, `stdout`, `stderr`, `token*`, `authorization`,
`password`, `passphrase`, `secret*`, `identity_file`, `private_key`, `env`, `environment`,
`cookie`, `credentials`), at any depth, becomes `"[redacted]"`, and token patterns are
removed from every string. The entry gains `device_id` (§6.2) and the public `action`
(§10.1). Reading is **newest first, backwards from the end of the file in chunks**
(`automations.read_audit_reverse`) and stops at `limit` (default 100, max 1000) — the
whole history is never loaded for one request. Filters: `device` (id or alias), `actor`,
`action` (public or job name), `decision`, `kind`, `job_id`, `rule`, `correlation_id`,
`since` (stops reading once entries are older). No query language.

## 23. OpenAPI recommendation

**Maintain a handwritten OpenAPI 3.1 document (`docs/openapi.yaml`) and pin it with a
hermetic test; do not generate it and do not adopt a framework.**

- The server is a stdlib `http.server` handler with an explicit route table (method,
  path pattern, scope, handler). A test asserts the route table and the spec's `paths`
  are the same set, that every `LP-` code in §15's table appears in the spec's error
  enum, and that each schema's `required` + `properties` names match the pinned
  dataclass field lists in `tests/test_contracts.py` — the same "snapshot the surface"
  discipline the contracts already use. Drift fails a test.
- Generation from dataclasses is possible with a 100-line stdlib script and is reserved for
  when the SDK is generated (`docs/vision.md`: `from linkplane import Phone`); until then
  a handwritten spec is smaller, reviewable, and can carry descriptions the dataclasses
  lack.
- `GET /v1/openapi.json` serving the file is a nice-to-have for the GUI and MCP adapter
  authors; include it in slice 2 (no scope needed beyond authentication).

## Founder Decisions Required (as put to the founder; resolved above)

### D1 — Where the API runs

**Question.** Should the HTTP API be hosted inside `linkplaned`, or be a separate process
that talks to the daemon over the control socket?

- **Option A (recommended): inside `linkplaned`.** One process owns observer, history
  (`seq`), job runner (duplicate set), audit writer, rules; the API is a second listener on
  the same objects. `daemon run` gains the listener; `daemon install` installs it.
- **Option B: separate `linkplane api` process.** Uses the socket for state/subscribe and
  calls services directly for actions — which requires its own `JobRunner` (a second
  running-set, so a rule and a client could run two backups at once) and its own audit
  writer, or a socket protocol widened to carry every action, job, and audit op.

**Recommended:** A. **Reason:** the invariants forbid a second job/event/error model, and
ADR 0008 already names the daemon as the API host. **If B is chosen:** the socket protocol
becomes the real API and HTTP a proxy of it; expect a `linkplane.daemon/2` protocol with
`action`, `jobs`, `cancel`, `audit` ops before any HTTP work, and accept that the daemon
must still be the sole `JobRunner`.

### D2 — Listener and authentication default

**Question.** Loopback TCP with a bearer token, or HTTP over a Unix socket?

- **Option A (recommended): `127.0.0.1:8741` + bearer token, always required.** Works for
  browsers' `EventSource`, every SDK, `curl`, and a webview GUI. The token closes the
  "any local user can reach loopback" gap. Discovery via `api.json`.
- **Option B: HTTP over `$XDG_RUNTIME_DIR/linkplane/api.sock` (0600), token still required
  to distinguish clients.** Strictly same-user by the kernel; but no browser, no
  `EventSource`, awkward for Node/Go SDKs, and every client needs the socket path.

**Recommended:** A. **Reason:** the GUI, SDK, and MCP clients are all HTTP-shaped; a
0600 socket protects against other local users, which the mandatory token also does.
**If B is chosen:** the design is unchanged except §19; a later TCP listener would be
opt-in. (Sub-question, low stakes: is the API listener **on** by default when the daemon
runs — recommended yes, since nothing can authenticate until a client is created — or
opt-in with `--api`?)

### D3 — URL versioning

**Question.** `/v1/devices` or `/v1/devices` with protocol tag `linkplane.api/1`?

- **Option A (recommended): unversioned paths + `linkplane.api/1`** in `/v1/health`, the
  `Linkplane-Api` header, `api.json`, and the stream message; records keep their `schema`
  tags. Matches every existing versioned record and does not promise 1.0 stability that
  `0.x` does not have.
- **Option B: `/v1/` prefix.** Conventional, lets `/v2` coexist in place, but adds a fourth
  version number to the project's policy and implies a frozen contract now.

**Recommended:** A. **Reason:** `docs/versioning.md` already has three deliberate version
kinds; the record-level `schema` pattern is the project's idiom. **If B is chosen:** every
path in this document gains `/v1`; nothing else changes; the milestone tag stays `api-v0.1`.
**Founder chose B** (§20, §26): the explicit major now is cheaper than retrofitting it once
SDKs and third-party clients exist.

### D4 — Job and rule activity in the canonical event stream

**Question.** Should job transitions (and rule firings) become canonical `Event`s
(`source: "jobs"` / `"rules"`, written to history with a `seq`, matchable by rules), or
stay their own record types multiplexed on the stream as `job` / `audit` messages?

- **Option A (recommended for this milestone): separate record kinds on the stream**
  (`event: job`, `event: audit`), `Event` stays "observed domain changes only" (ADR 0007).
  No history growth, no rule loops, no new event types; catch-up via `GET /v1/jobs` /
  `/v1/audit`.
- **Option B: job/rule events in the canonical stream.** One event language for the GUI
  and rules (a rule could react to `job.completed` — "notify me when the backup
  finishes"); costs: history doubles in write rate during transfers, rule chains can loop
  (backup → job.completed → rule → backup) unless a depth limit is designed, and the
  `EVENT_TYPES` catalogue grows by six.

**Recommended:** A now; revisit B when a rule-chaining feature is actually wanted, at which
point `Event.source` and `correlation_id` already make it additive. **If B is chosen now:**
add the six `job.*` types to `EVENT_TYPES`, emit them from the transition hook through the
daemon sink (so they get a `seq`), and add a firing-depth guard to `Engine` before shipping.

### D5 — Default scope grant and the sensitive set

**Question.** Is the `read` default (`device.read device.state.read events.read jobs.read
rules.read`) the right zero-argument grant, and is `audit.read` correctly excluded from it?

- **Option A (recommended): as designed** — `read` excludes `audit.read`; every action
  scope must be named; sensitive scopes print a warning when granted.
- **Option B: `read` includes `audit.read`,** on the grounds that the audit log is the
  user's own activity history and a GUI will want it immediately.

**Recommended:** A. **Reason:** the audit log carries `run` stdout, SSIDs, file names, and
action parameters; a Waybar module or an AI agent does not need it. **If B is chosen:**
only the CLI shorthand changes; the model is unchanged.
