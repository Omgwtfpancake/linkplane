# Linkplane v0.6 direction: automatic usefulness

Status: **approved by the founder** (2026-09-16). Slice 1 (automatic photo backup preset)
is implemented on the `dev/v0.6` branch, unreleased; see §12. Written after the first
external alpha feedback ([`alpha-feedback.md`](alpha-feedback.md)) against the code at
package version 0.5.1.

Founder decisions: backup is the v0.6 proof; the feature is called **backup**, not sync;
setup asks before enabling it, with no silent default; the faster unchanged-file check is
built only if measurement shows it is needed.

Guiding principle: *Linkplane should solve work the user would otherwise have to repeatedly
do by hand.*

## 1. Audit: what exists today

Classification: **User-facing** (implemented and easy to reach) · **Foundation** (implemented
but not easy for users) · **Partial** · **Not implemented** · **Deferred** (a deliberate
decision not to build yet).

| Area | Status | Evidence and gap |
|---|---|---|
| Events | **User-facing** | `core/events.py`, `observe.py`: `device.connected/disconnected/authorized/unauthorized`, `battery.changed/low/ok`, `charging.started/stopped`, `wifi.connected/disconnected`, `observer.*`; identified, sequenced, correlated, persisted to `events.jsonl`; `linkplane events [--follow]`; SSE on the API. No `files.added` or time events. |
| Rules | **Foundation** | `core/automation.py` (when / if / do, operators, placeholders, cooldown, `on_initial`, `continue_on_error`, consent-gated `run`), hosted in the daemon (ADR 0009), `daemon reload`, `automations list|log`. Only reachable by hand-writing `automations.json`; no CLI to add, enable or disable a rule; setup never mentions it. |
| Jobs | **Foundation** | `jobs.py`: job-tracked `backup`, `send`, `clipboard-sync` with records, progress, retry on lost connection, cancel on disconnect, one per device and action, results feeding later steps (`{downloaded}`); `automations jobs`; API `/v1/jobs`. Visible only if you already use rules or the API. |
| Scheduled behaviour | **Not implemented** | No time or interval trigger. The only periodic work is the observer's 30 s battery / Wi-Fi poll. |
| Triggered behaviour | **Foundation** | Any event type can trigger rules; `linkplane watch` runs one rule in the foreground from flags. Conditions test only the triggering event's data, not current state (e.g. "and charging" cannot be added to `device.connected`). No per-step condition ("notify only if something was downloaded"). |
| File send | **User-facing** | `linkplane send` over ADB, LocalSend fallback; `send` rule action. Not incremental, not resumable. |
| Backup | **User-facing** (manual) / **Foundation** (automatic) | `backup.py`: one Android source directory to one local destination, manifest bound to device and source, temp file plus SHA-256 verification, never deletes local copies, resumes by manifest. Automatic only through a hand-written rule. Every run re-hashes every already-backed-up local file. No free-space check. |
| Synchronisation | **Partial** | Backup is one-way, additive phone → computer sync in all but name. Clipboard sync is foreground (or a daemon job) and needs Termux:API. No computer → phone delivery sync, no two-way file sync. |
| Wireless ADB | **Partial** | `pair wireless` (pairing code, never in argv), wireless aliases in profiles, `profiles refresh [--scan]` verified against a USB-learned serial. The observer sees a wireless device only after something has run `adb connect`; the daemon never connects or reconnects on its own; setup is USB-only. |
| Daemon startup / observation | **User-facing** | `linkplaned`, systemd user unit installed and started by `setup`, `adb track-devices` push plus polls, `state.json`, control socket, `daemon status`, clean SIGTERM, survives reboot (onboarding run 002). |
| Desktop notifications | **Foundation** | `notify-desktop` rule action via `notify-send`; `doctor` reports availability. No command sends one directly, and nothing notifies by default. |
| System tray / GUI | **Not implemented** (deferred by the Core v0.1 brief) | No tray, window, or bar module. The local API was designed with such clients in mind (`client:waybar` examples). |
| Device-connect hooks | **Foundation** | `device.connected` rules with `run`, `backup`, `send`, `notify-*`. A phone already plugged in when the daemon starts produces an *initial* observation, which rules ignore unless `on_initial` is set. |
| Local API | **Foundation** (developer-facing) | `api/`: `/v1` devices, state, capabilities, actions, jobs and cancel, events and SSE, rules (read, reload), audit; bearer tokens with scopes; `docs/openapi.json`. Rules cannot be created or toggled over the API. |
| Provider abstraction | **Foundation** | `providers/`: ADB and SSH behind one contract, capability catalogue with five statuses, `LP-` coded errors (ADR 0002, 0004–0006). |

**Conclusion: v0.6 does not need a new automation engine.** Events, rules, jobs, audit,
the daemon and the API already express "when the phone connects, back up new photos, then
tell me". v0.6 needs to *expose* that engine as a workflow a user can switch on in one step,
plus a few small, additive engine refinements the workflow exposes (section 4).

Can today's engine express the three example automations?

| Automation | Today |
|---|---|
| WHEN phone connects THEN run photo backup | **Yes**: `{"when": "device.connected", "do": [{"action": "backup", ...}]}`. Misses the phone that is already connected at login unless `on_initial` is set. |
| WHEN battery < 20% THEN desktop notification | **Yes**: `battery.low` (threshold `--low-battery`, default 20) with `notify-desktop`. |
| WHEN phone joins trusted Wi-Fi THEN make wireless connection available | **No.** `wifi.connected` is only observed while the phone is already reachable over ADB (usually USB), and there is no action that runs `adb connect` or `adb tcpip`. |

## 2. The v0.6 outcome

> **Linkplane v0.6 proves that the phone does useful work because it is connected and
> observed, without the user issuing the command.**

The concrete proof: *plug the phone in, walk away, and new photos are on the computer,
verified, with one desktop notification saying so*, switched on with a single yes during
setup.

Evaluation of the candidates:

| Candidate | In v0.6? | Why |
|---|---|---|
| A. Automatic action on connection / event | **Yes (the core)** | The engine exists; this is exposure work, and it answers "does it do anything by itself?" |
| B. Selected-folder / photo synchronisation | **Yes, as one-way backup only** | It is the most obviously useful automatic action, and backup already exists. It is the action A runs. |
| C. Better wireless operation / onboarding | **No** | Real gap, but it needs daemon-side connect/reconnect logic, Android wireless-debugging port behaviour and security review. It does not prove anything A+B do not already prove over USB. Next milestone. |
| D. Tray / quick actions | **No** | A tray over a manual product is still manual. It becomes valuable once there is automatic behaviour to show and toggle. Follows the automation milestone. |

A + B is the smallest combination that proves the thesis. A alone ("notify when connected")
is a demo; B alone is a better `adb pull`.

## 3. Exact v0.6 scope

1. **Automatic photo backup preset.** A built-in, named preset that writes ordinary rules
   into `automations.json` (no second engine): when the phone connects, including a phone
   already connected when the daemon starts, back up the camera folder (and, as an option,
   screenshots) to a chosen folder, then send one desktop notification only if something new
   arrived.
2. **One-step opt-in.** `linkplane setup` offers it at the end with a clear question and the
   destination folder (default off until the user says yes; re-running setup shows its
   state). A CLI to list, enable and disable presets and existing rules, so nobody has to
   edit JSON to turn it off.
3. **Visible outcome.** The last automatic backup (when, how many files, success or error)
   appears somewhere the user already looks: `linkplane status` and `daemon status`, and the
   notification.
4. **Engine refinements the workflow needs** (additive, tested, no schema break):
   - a step-level condition over earlier results, so the notification can be skipped when
     `downloaded` is 0;
   - the preset sets `on_initial` for `device.connected` (backup is idempotent), and the docs
     explain why;
   - a fast path for unchanged files (size + mtime match, full re-hash only on demand or
     periodically) if measurement on a large real library shows the per-connect re-hash is
     too slow, plus a free-space check before downloading.
5. **Proof.** A device test and a clean-machine run of the automatic flow; the alpha tester
   guide gets a second session ("turn on automatic backup, replug, check the folder").

CLI syntax is **not decided** here. It should follow existing noun-verb conventions
(`automations list|log|jobs`, `profiles list|default|remove|refresh`, `clients
create|list|revoke`), for example presets under `automations`. Whether the user-facing
word is "backup" or "sync" is an open founder question (section 5 recommends "backup").

## 4. Explicitly excluded from v0.6

- tray, bar module, or any GUI
- wireless onboarding, automatic `adb connect` / reconnect, Wi-Fi-triggered connection
- two-way sync, computer → phone delivery sync, deletion propagation, delete-after-backup
- time or interval triggers, state-based conditions ("only while charging")
- `files.added` events or phone-side file watching
- rule editing over the local API, a visual rule builder
- native Android agent, MCP / AI integration
- macOS or Windows work, new providers
- new capabilities unrelated to the automatic backup workflow

## 5. Sync: what it should mean

| Mode | Meaning | Recommendation |
|---|---|---|
| One-way phone → computer backup | Copy new and changed phone files to the computer; never touch the phone; never delete local copies | **v1 (v0.6).** Exists as `backup`. |
| One-way computer → phone delivery | Keep a phone folder supplied from a computer folder (music, documents, APKs) | Later. Needs an incremental, manifest-based `send`, and a deletion policy on the phone. |
| Bidirectional sync | Dropbox-style convergence | Not planned. Conflict and deletion semantics are hard and dangerous; Syncthing already does this well and Linkplane should complement it. |
| Scheduled sync | Run every N hours while connected | Later; needs a time trigger. |
| Sync on connection | Run when the phone connects | **v1.** |
| Sync on home Wi-Fi | Run when the phone joins a trusted network | After wireless (the phone must be reachable without a cable). The rule itself is already expressible. |

Behaviour for v1 (mostly how `backup` already works; items marked *new* are v0.6 work):

- **Direction:** phone → computer only. Linkplane never deletes or modifies phone files.
- **Scope:** explicit Android folders (camera by default, screenshots optional), each to its
  own local subfolder (the manifest is bound to device + source).
- **Deletions:** a file deleted on the phone stays on the computer. Never propagated.
- **Changes:** a phone file whose size or mtime changed is downloaded again and replaces the
  local copy. A local copy that no longer matches its checksum is treated as damaged and
  replaced. The destination is Linkplane-owned: document that users should copy, not edit,
  files there. (Keeping previous versions is a later option.)
- **Conflicts:** none in one-way mode by construction; a destination belonging to another
  device or source is refused (already enforced).
- **Resumability:** each file is written to a temporary file and verified before it
  replaces anything; an interrupted run leaves the manifest consistent and the next run
  continues (already). Retry on lost connection and cancel on disconnect (already, as a job).
- **History / audit:** job records and audit entries with the correlation id of the
  connect event (already); *new*: last-backup summary in `status`.
- **Safety:** *new* free-space check; no action on a phone that is `unauthorized`; one backup
  job per device at a time (already); nothing runs until the user opted in.

Recommendation on naming: call v1 **automatic backup**, not "sync". "Sync" promises
two-way convergence to most people, and v1 deliberately does not do that. Reserve `sync`
for when delivery or two-way modes exist.

## 6. Automation UX

Principle: ordinary users choose **presets**; power users edit rules; programs use the API.
All three produce the same `automations.json` rules, run by the same daemon, recorded in the
same audit log.

- **Presets** are named, documented bundles of rules with a few parameters (destination,
  include screenshots). Enabling one writes rules marked as belonging to that preset;
  disabling removes or disables them; `automations list` shows them by preset name.
- **Setup** offers the one preset that proves the product (automatic photo backup). Nothing
  else is offered in v0.6.
- **`linkplane watch`** stays the foreground, try-it-now form of a single rule.
- **Explainability:** `automations log` already says what fired and why; the v0.6
  notification and `status` line make the result visible without opening a log.
- **Later presets** (not v0.6): low-battery desktop notification (expressible today, a good
  second preset), "home network" presets once wireless exists, delivery folders once
  delivery sync exists.

## 7. Tray UI (after v0.6)

The tray is a **client of the control plane**: it reads `/v1/devices`, `/v1/devices/{id}/state`,
`/v1/jobs` and the SSE stream, and calls `/v1/devices/{id}/actions`. It holds no device logic,
no rules engine and no state of its own; if the daemon is stopped it says so.

Responsibilities, in priority order: connection indicator and device name; battery;
last automatic backup and "back up now"; enable / pause automatic backup; mirror screen;
send file; open diagnostics (`doctor`); switch device when there are several.

Gaps the tray will expose in the API (to plan, not build now): toggling a preset or rule
(the API only reads and reloads rules), launching a local foreground tool such as scrcpy
from a client, and client provisioning without a terminal. Linux trays differ by desktop
(StatusNotifierItem vs. Waybar-style bars); a Waybar module over the API is a cheap first
client and a good way to validate the API before a full tray.

**Recommendation:** v0.7 or later, after automatic backup ships. A toggle for automatic
backup is the tray's most important control, so the tray should follow it.

## 8. Wireless

Gap between "wireless ADB exists" and "wireless feels automatic":

| Exists | Missing |
|---|---|
| `pair wireless` with a pairing code | wireless as part of `setup` |
| wireless aliases in profiles | the daemon connecting to a known phone on its own |
| `profiles refresh [--scan]` with serial verification | reconnecting after sleep, Wi-Fi changes or an IP / port change |
| observer sees a wireless serial once connected | discovery of the phone's current wireless-debugging port (Android changes it; mDNS via `adb mdns` is unused) |
| `wifi.connected` event (only while already reachable) | knowing the phone is home when there is no cable |

Security needs deliberate design: automatic connection must stay bound to a verified
device identity (as `--scan` already is), on trusted networks only, and must never leave
pending authorization prompts on someone else's phone.

**Recommendation:** not v0.6. Make **wireless reconnection for already-paired phones** the
next milestone after automatic backup, because it turns "back up on connect" into "back up
when I get home", which is where automatic usefulness compounds.

## 9. Host platform preparation (light review, no port)

Linux-specific concerns and where they live today:

| Concern | Location | Assessment |
|---|---|---|
| Service management | `service.py` (systemd user unit), `uninstall.py` | Already isolated; the module docstring calls it the only Linux-desktop-specific piece of the control plane. A launchd / Windows equivalent is a sibling module. |
| Dependency installation | `dependencies.py` | Package-manager plans are data (pacman, apt-get, dnf, brew already). Fine. |
| Desktop notifications | `actions.py` (`notify-send`), `doctor.py` | One function; extract to a small host module when a second platform arrives. |
| Clipboard | `clipboard.py` (`wl-copy`/`wl-paste`, `xclip`) | Contained in one module. Fine. |
| Filesystem locations | `paths.py` (XDG) | Central; one function per root. Fine. |
| Daemon control socket | `daemon.py` (Unix socket in `$XDG_RUNTIME_DIR`) | The largest future Windows cost. The local HTTP API is already the portable interface; keep new clients on it. |
| Process launching | scrcpy wrappers (`screen.py`, `webcam.py`, `audio.py`) | Argument arrays; `webcam` is inherently Linux (V4L2). |
| Optional tool discovery | `shutil.which` + dependency catalogue | Portable. |

**Recommendation:** no refactor now; the architecture does not make ports significantly
harder. Two cheap rules for v0.6 code: new desktop-facing effects (notifications, opening a
folder) go through one small function rather than new direct `notify-send` / `xdg-open`
calls scattered across modules; and new clients (tray, bar) use the HTTP API, not the Unix
control socket.

## 10. Roadmap

No dates. Each milestone has one outcome.

**v0.5.x: alpha feedback and fixes.** Onboarding and documentation fixes from testers
(v0.5.1 shipped), README positioning (this pass), bug fixes only.

**v0.6: automatic usefulness.** Automatic photo backup on connect as a one-step opt-in
preset, visible results, the small engine refinements it needs, proven on a clean machine
(sections 2–5).

**Later, in the recommended order:**

1. Wireless reconnection for paired phones ("back up when I get home").
2. Tray / bar client over the local API, with automatic-backup toggle.
3. More presets and triggers: low-battery notification, time triggers, state conditions,
   computer → phone delivery folders.
4. Native Android agent (phone-side events such as new files, capabilities ADB cannot reach).
5. MCP / AI integration over the local API with approval gates.
6. Multi-device expansion (several phones, device groups).
7. macOS, then Windows, behind a host abstraction.

## 11. Open questions for the founder

1. Is "automatic photo backup on connect" the right single proof, or should delivery
   (computer → phone) be the proof instead? (Recommendation: backup.)
2. User-facing word: "automatic backup" now and `sync` later, or `sync` from v0.6?
3. Should setup offer the preset with a default of yes or no? (Recommendation: ask
   explicitly, no silent default.)
4. Is the per-connect re-hash of an existing library acceptable, or must the fast path be
   in v0.6? Decide after measuring on a real library.

## 12. Slice 1 status (dev/v0.6, unreleased)

Implemented:

- **Step-level conditions** in the rule engine (`core/automation.py`): a step's `if` is
  tested against the event data plus earlier results; unmet means skipped, not failed.
  Rules gain an informational `preset` marker.
- **Preset** `photo-backup` (`presets.py`): one ordinary rule per device profile,
  `device.connected` with `on_initial`, `backup` of `/sdcard/DCIM/Camera`, then
  `notify-desktop` only if `downloaded > 0`. No shell action. Enable validates the folder
  and never rewrites an invalid rules file; disable keeps the rule and all backups.
- **CLI**: `linkplane automations presets|enable|disable`; `automations list` shows the
  preset and step conditions; `GET /v1/rules` includes `preset` and step `if`.
- **Setup**: after every check passes on the run that registers a phone, one explained
  question (default no), a folder prompt, and a daemon restart so the first backup starts
  immediately. Reruns never ask again.
- **Backup safety**: free-space check before downloading (`LP-STORAGE-001`, HTTP 507);
  untracked local files are never overwritten (identical ones are recorded); writing
  through a symlink in the destination is refused.
- **Visibility**: `linkplane status` shows whether automatic backup is on and its last run,
  derived from job records (no new state file). Failures are in `automations jobs` and the
  audit log.
- **Measurement**: `BackupResult` records discovery, unchanged-check and total seconds and
  bytes verified; `tools/measure-backup.py` measures against a phone (dry run) or a
  synthetic library. A synthetic 4 GB library re-hashes at about 1.5 GB/s on the
  development machine (RAM-backed, warm cache), so re-hashing a 20 GB library costs roughly
  15 s warm; cold-disk cost and per-file `adb stat` discovery on a real phone are **not yet
  measured** and are the first job of Slice 2.

Findings:

- The observer marks a device's first connection after daemon start as *initial* even when
  the phone is plugged in later, so hand-written `device.connected` rules without
  `on_initial` miss the first plug-in after login. Left unchanged globally (founder: do not
  change initial semantics for unrelated rules); worth an explicit decision.
- A setup rerun does not offer the preset to a phone registered before v0.6 (so it never
  nags); such users enable it with `linkplane automations enable photo-backup`.
- Automatic backup failures are visible in jobs, the audit log and `status`, but do not
  notify the desktop; the engine stops at the failed step and there is no failure-notice
  convention yet.
